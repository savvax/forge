# CardPay Integration Guide

> Generated by forge 1.0.0 from CardPay Transfers API 2.3.0. Решения с confidence < 0.8 перечислены в разделе «Допущения».

## Кратко

- Провайдер: **CardPay**; спецификация CardPay Transfers API 2.3.0 (`examples/specs/cardpay.yaml`).
- Сервис: `Provider::CardpayService` (`cardpay_service.rb`) реализует контракт `Provider::BaseService`: `check_conditions`, `create_request`, `fetch_status`, `process_callback`.
- API: `https://sandbox.cardpay.example/v2` (sandbox по умолчанию), production `https://api.cardpay.example/v2`; авторизация — Bearer token.
- Выплата создаётся `POST /transfers`, статус — `GET /transfers/{transfer_id}` и webhook `POST {$request.body#/callback_url}`; итог операции — `in_progress` / `approved` / `rejected`.
- Заполнить вручную: `credentials.token`, `credentials.callback_secret`, `credentials.merchant_id`; все допущения анализа — в разделе «Допущения».

## Как платформа работает с сервисом

- `check_conditions(operation, request_method)` — предпроверки до запроса (раздел «Проверки перед отправкой»); `request_method` — тип реквизитов (`card`) либо служебное `status` / `check`.
- `create_request(operation, request_method)` — собирает тело по таблице «Поля запроса» и шлёт `POST /transfers`; успех — HTTP 201; id выплаты сохраняется в `operation.provider_operation_key` из `data.transfer_id`. `request_method` `status`/`check` делегируется в `fetch_status`.
- `fetch_status(operation)` — `GET /transfers/{transfer_id}`, статус из `data.state` по «Маппингу статусов».
- `process_callback(payload, raw_body:, headers:)` — проверяет подпись `X-Signature`, берёт событие из `type`, находит операцию по `data.transfer_id` и переводит её в approved / rejected / in_progress.
- Ошибки провайдера → `failure` по таблице «Обработка ошибок» (семантика действий — там же).

## Авторизация

- Тип: Bearer token
- Header: `Authorization: Bearer <credentials.token>`
- Хранение: `providers.credentials` (encrypted)
- Заполнить вручную: `credentials.token`, `credentials.callback_secret`, `credentials.merchant_id`

### create_payout — POST /transfers

- Успех: HTTP 201; id выплаты — `data.transfer_id`, статус — `data.state`.
- Тело: json; заголовки: авторизация.
- Ошибки: HTTP 400, 401, 403, 422, 500, 503 — см. «Обработка ошибок».

Пример запроса (`fixtures.json`):

```json
{
  "merchant_id": "m_10042",
  "reference": "op_abc123",
  "amount": "1500.00",
  "currency": "RUB",
  "description": "Payout op_abc123",
  "callback_url": "https://spacepayments.example/webhooks/cardpay",
  "destination": {
    "card": {
      "pan": "4111111111111111",
      "holder": "IVAN IVANOV",
      "expiry": "12/29"
    }
  }
}
```

Пример ответа 201 (`fixtures.json`):

```json
{
  "data": {
    "transfer_id": "tr_9c1e4f",
    "reference": "op_abc123",
    "state": "NEW",
    "amount": "1500.00",
    "currency": "RUB"
  }
}
```

### get_status — GET /transfers/{transfer_id}

- Успех: HTTP 200; id выплаты — `data.transfer_id`, статус — `data.state`.
- Ошибки: HTTP 401, 404 — см. «Обработка ошибок».

Пример ответа 200 (`fixtures.json`):

## Сумма и валюта

- Поле `amount` (string): мажорные единицы — `format('%.2f', operation.amount)`.
- Валюты: RUB, USD; поле `currency`, иная валюта → `currency_not_supported`.

## Реквизиты получателя (`operation.payout_requisite`)

Тип реквизитов приходит в `request_method` и выбирает набор полей; значение для провайдера — см. «Поля запроса».

| Тип | Поля из `payout_requisite` (обязательность) |
|-----|---------------------------------------------|
| card | `pan` (да), `holder` (да), `expiry` (нет) |

## Проверки перед отправкой (`check_conditions`)

Базовые проверки `Provider::BaseService` (сумма положительна, валюта и реквизиты заданы) плюс правила из схемы запроса:

| Поле | Правило | Код ошибки |
|------|---------|------------|
| reference | длина ≤ 40 | reference_too_long |
| currency | один из: RUB, USD | currency_not_supported |
| description | длина ≤ 140 | description_too_long |
| destination.card.pan | формат `^\d{13,19}$` (тип `card`) | pan_invalid |
| destination.card.expiry | формат `^(0[1-9]|1[0-2])/\d{2}$` | expiry_invalid |

## Маппинг статусов

| Provider | Space Payments |
|----------|----------------|
| NEW | in_progress |
| PROCESSING | in_progress |
| SUCCESS | approved |
| DECLINED | rejected |
| ON_HOLD | in_progress |

## События webhook

| Event | Space Payments |
|-------|----------------|
| transfer.settled | approved |
| transfer.declined | rejected |
| transfer.on_hold | in_progress |

## Обработка ошибок

| HTTP | Provider code | Действие |
|------|---------------|----------|
| 400 | validation_error | reject |
| 401 | unauthorized | alert ops, block provider |
| 403 | forbidden | alert ops, block provider |
| 404 | not_found | reject |
| 422 | validation_error | reject |
| 500 | internal_error | retry, alert ops |
| 503 | issuer_unavailable | retry with backoff |

Что означают действия:

- **reject** — операция отклоняется: `failure(<http>, "provider.<code>")`, платформа не повторяет запрос.
- **retry later** / **retry with backoff** — временная ошибка: `failure` с `retry_after` из `Retry-After`, если провайдер его прислал; платформа повторяет позже.
- **alert ops, block provider** — неверные учётные данные: `provider.invalid_credentials`, провайдер блокируется до вмешательства.
- **treat as success** — идемпотентный повтор (тот же `Idempotency-Key`): ответ читается как успешный.
- Сеть, таймаут, 5xx → `provider.unavailable`; 429 → `provider.rate_limit`.

## Приём webhook

- Эндпоинт провайдера: `POST {$request.body#/callback_url}` (источник: `callbacks` эндпоинта создания).
- Адрес приёма на стороне Space Payments — `config.callback_url`; его нужно зарегистрировать у провайдера.
- Поле события: `type`; поле статуса: `data.state`; id выплаты: `data.transfer_id`.
- Повторная доставка того же события безопасна: переход в тот же статус идемпотентен.
- Проверка на моке: `POST /_simulate/<id>/<event>` — мок шлёт подписанный webhook на `WEBHOOK_URL`.

Успешное событие → `approved` (`fixtures.json`):

```json
{
  "type": "transfer.settled",
  "data": {
    "transfer_id": "tr_9c1e4f",
    "reference": "op_abc123",
    "state": "SUCCESS"
  }
}
```

Неуспешное событие → `rejected` (`fixtures.json`):

```json
{
  "type": "transfer.declined",
  "data": {
    "transfer_id": "tr_9c1e4f",
    "reference": "op_abc123",
    "state": "DECLINED",
    "error": {
      "code": "card_declined",
      "message": "Issuer declined the transfer"
    }
  }
}
```

## Webhook signature

HMAC-SHA512(body, callback_secret) → base64 → X-Signature

Подпись считается по сырым байтам тела. Платформа передаёт в `process_callback` уже разобранный JSON, поэтому передавайте и сырое тело: `process_callback(payload, raw_body: request.body.read, headers: request.headers)`. Без `raw_body` сервис подписывает `JSON.generate(payload)` — подпись сойдётся, только если провайдер шлёт компактный JSON с тем же порядком ключей.

## Поля запроса

| Поле | Источник | Обязательность | Преобразование |
|------|----------|----------------|----------------|
| merchant_id | `credentials.fetch('merchant_id')` | да | - |
| reference | `operation.id.to_s` | да | to_s |
| amount | `format('%.2f', operation.amount)` | да | amount |
| currency | `operation.currency` | да | - |
| description | `operation.description || "Payout #{operation.id}"` | нет | - |
| callback_url | `callback_url` | да | - |
| destination.card.pan | `operation.payout_requisite.dig('card', 'card_number')` | да | - |
| destination.card.holder | `operation.payout_requisite.dig('card', 'holder')` | да | - |
| destination.card.expiry | `format('%02d/%02d', operation.payout_requisite.dig('card', 'expiry_month'), operation.payout_requisite.dig('card', 'expiry_year') % 100)` | нет | - |
