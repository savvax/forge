# SwiftPay Integration Guide

> Generated by forge 1.0.0 from SwiftPay Outbound Payments 3.0.1. Решения с confidence < 0.8 перечислены в разделе «Допущения».

## Кратко

- Провайдер: **SwiftPay**; спецификация SwiftPay Outbound Payments 3.0.1 (`examples/specs/swiftpay.json`).
- Сервис: `Provider::SwiftpayService` (`swiftpay_service.rb`) реализует контракт `Provider::BaseService`: `check_conditions`, `create_request`, `fetch_status`, `process_callback`.
- API: `https://sandbox.swiftpay.example/api` (sandbox по умолчанию); авторизация — Basic auth.
- Выплата создаётся `POST /v1/payments/outbound`, статус — `GET /v1/payments/outbound/{payment_id}` и webhook `POST paymentStatusChanged`; итог операции — `in_progress` / `approved` / `rejected`.
- Заполнить вручную: `credentials.login`, `credentials.password`, `credentials.callback_secret`; все допущения анализа — в разделе «Допущения».

## Как платформа работает с сервисом

- `check_conditions(operation, request_method)` — предпроверки до запроса (раздел «Проверки перед отправкой»); `request_method` — тип реквизитов (`bank_account`) либо служебное `status` / `check`.
- `create_request(operation, request_method)` — собирает тело по таблице «Поля запроса» и шлёт `POST /v1/payments/outbound`; успех — HTTP 201, 409; id выплаты сохраняется в `operation.provider_operation_key` из `payment_id`. `request_method` `status`/`check` делегируется в `fetch_status`.
- `fetch_status(operation)` — `GET /v1/payments/outbound/{payment_id}`, статус из `status` по «Маппингу статусов».
- `process_callback(payload, raw_body:, headers:)` — проверяет подпись `Swift-Signature`, берёт статус из `data.status`, находит операцию по `data.payment_id` и переводит её в approved / rejected / in_progress.
- Ошибки провайдера → `failure` по таблице «Обработка ошибок» (семантика действий — там же).

## Авторизация

- Тип: Basic auth
- Header: `Authorization: Basic base64(<credentials.login>:<credentials.password>)`
- Хранение: `providers.credentials` (encrypted)
- Заполнить вручную: `credentials.login`, `credentials.password`, `credentials.callback_secret`

## Настройка

- ENV `SWIFTPAY_BASE_URL` — базовый URL (default sandbox: `https://sandbox.swiftpay.example/api`)
- `config.callback_url` — адрес приёма webhook на стороне Space Payments
- ProviderGateway config — см. раздел ниже

Все ключи, которые нужно задать до первого запроса:

| Ключ | Назначение |
|------|------------|
| ENV `SWIFTPAY_BASE_URL` | базовый URL; по умолчанию sandbox `https://sandbox.swiftpay.example/api` |
| `credentials.login` | авторизация (Basic auth), выдаёт провайдер |
| `credentials.password` | авторизация (Basic auth), выдаёт провайдер |
| `credentials.callback_secret` | секрет подписи webhook, выдаёт провайдер |

### create_payout — POST /v1/payments/outbound

- Успех: HTTP 201, 409 (409 — повтор по Idempotency-Key, читается как успех); id выплаты — `payment_id`, статус — `status`.
- Тело: json; заголовки: авторизация и `Idempotency-Key: operation.idempotency_key`.
- Ошибки: HTTP 400, 401, 422, 500 — см. «Обработка ошибок».

Пример запроса (`fixtures.json`):

```json
{
  "reference": "op_abc123",
  "amount": 1500.5,
  "currency": "EUR",
  "purpose": "Payout op_abc123",
  "beneficiary": {
    "name": "Ivan Ivanov",
    "iban": "DE89370400440532013000",
    "bic": "COBADEFFXXX",
    "address": {
      "country": "DE",
      "city": "Berlin",
      "line1": "Unter den Linden 1"
    }
  }
}
```

Пример ответа 201 (`fixtures.json`):

```json
{
  "payment_id": "pay_01H9",
  "reference": "op_abc123",
  "status": "CREATED",
  "amount": 1500.5,
  "currency": "EUR"
}
```

### get_status — GET /v1/payments/outbound/{payment_id}

- Успех: HTTP 200; id выплаты — `payment_id`, статус — `status`.
- Ошибки: HTTP 401, 404 — см. «Обработка ошибок».

Пример ответа 200 (`fixtures.json`):

```json
{
  "payment_id": "pay_01H9",
  "reference": "op_abc123",
  "status": "SETTLED",
  "amount": 1500.5,
  "currency": "EUR"
}
```

## Сумма и валюта

- Поле `amount` (number): мажорные единицы — `operation.amount.to_f.round(2)`.
- Минимум: 1 (`check_conditions` → `amount_too_low`).
- Валюты: EUR, USD, GBP; поле `currency`, иная валюта → `currency_not_supported`.

## Реквизиты получателя (`operation.payout_requisite`)

Тип реквизитов приходит в `request_method` и выбирает набор полей; значение для провайдера — см. «Поля запроса».

| Тип | Поля из `payout_requisite` (обязательность) |
|-----|---------------------------------------------|
| bank_account | `name` (да), `iban` (да), `bic` (нет) |

## Проверки перед отправкой (`check_conditions`)

Базовые проверки `Provider::BaseService` (сумма положительна, валюта и реквизиты заданы) плюс правила из схемы запроса:

| Поле | Правило | Код ошибки |
|------|---------|------------|
| amount | ≥ 1 | amount_too_low |
| reference | длина ≤ 35 | reference_too_long |
| currency | один из: EUR, USD, GBP | currency_not_supported |
| beneficiary.iban | формат `^[A-Z]{2}\d{2}[A-Z0-9]{11,30}$` (тип `bank_account`) | iban_invalid |
| purpose | длина ≤ 140 | purpose_too_long |

## Маппинг статусов

| Provider | Space Payments |
|----------|----------------|
| CREATED | in_progress |
| SENT | in_progress |
| SETTLED | approved |
| REJECTED | rejected |

Не распознаны (задать в `overrides.yml` → `statuses.<STATUS>: in_progress|approved|rejected`): `PENDING_APPROVAL`, `RETURNED`

## Обработка ошибок

| HTTP | Provider code | Действие |
|------|---------------|----------|
| 400 | validation_error | reject |
| 401 | unauthorized | alert ops, block provider |
| 404 | not_found | reject |
| 422 | validation_error | reject |
| 500 | internal_error | retry, alert ops |

Что означают действия:

- **reject** — операция отклоняется: `failure(<http>, "provider.<code>")`, платформа не повторяет запрос.
- **retry later** / **retry with backoff** — временная ошибка: `failure` с `retry_after` из `Retry-After`, если провайдер его прислал; платформа повторяет позже.
- **alert ops, block provider** — неверные учётные данные: `provider.invalid_credentials`, провайдер блокируется до вмешательства.
- **treat as success** — идемпотентный повтор (тот же `Idempotency-Key`): ответ читается как успешный.
- Сеть, таймаут, 5xx → `provider.unavailable`; 429 → `provider.rate_limit`.

## Приём webhook

- Эндпоинт провайдера: `POST paymentStatusChanged` (источник: top-level `webhooks` спеки).
- Адрес приёма на стороне Space Payments — `config.callback_url`; его нужно зарегистрировать у провайдера.
- Поле события: `type`; поле статуса: `data.status`; id выплаты: `data.payment_id`.
- Повторная доставка того же события безопасна: переход в тот же статус идемпотентен.
- Проверка на моке: `POST /_simulate/<id>/<event>` — мок шлёт подписанный webhook на `WEBHOOK_URL`.

Успешное событие → `approved` (`fixtures.json`):

```json
{
  "id": "evt_5f1",
  "type": "payment.status_changed",
  "occurred_at": "2026-07-30T10:05:00Z",
  "data": {
    "payment_id": "pay_01H9",
    "reference": "op_abc123",
    "status": "SETTLED"
  }
}
```

Неуспешное событие → `rejected` (`fixtures.json`):

```json
{
  "id": "evt_5f2",
  "type": "payment.status_changed",
  "occurred_at": "2026-07-30T10:06:00Z",
  "data": {
    "payment_id": "pay_01H9",
    "reference": "op_abc123",
    "status": "REJECTED",
    "reason": {
      "code": "account_closed",
      "detail": "Beneficiary account is closed"
    }
  }
}
```

## Webhook signature

HMAC-SHA256("<t>.<body>", callback_secret) → hex → Swift-Signature: `t=<unix timestamp>,v1=<hmac>`

Подпись считается по сырым байтам тела. Платформа передаёт в `process_callback` уже разобранный JSON, поэтому передавайте и сырое тело: `process_callback(payload, raw_body: request.body.read, headers: request.headers)`. Без `raw_body` сервис подписывает `JSON.generate(payload)` — подпись сойдётся, только если провайдер шлёт компактный JSON с тем же порядком ключей.

## Поля запроса

| Поле | Источник | Обязательность | Преобразование |
|------|----------|----------------|----------------|
| reference | `operation.id.to_s` | да | to_s |
| amount | `operation.amount.to_f.round(2)` | да | amount |
| currency | `operation.currency` | да | - |
| beneficiary.name | `operation.payout_requisite.dig('bank_account', 'holder')` | да | - |
| beneficiary.iban | `operation.payout_requisite.dig('bank_account', 'iban')` | да | - |
| beneficiary.bic | `operation.payout_requisite.dig('bank_account', 'bic')` | нет | - |
| beneficiary.address | **TODO** (overrides.yml) | нет | - |
| purpose | `operation.description || "Payout #{operation.id}"` | нет | - |

## Допущения

| Решение | Источник | Уровень | Как переопределить |
|---------|----------|---------|--------------------|
| alternative security scheme 'oauth2' (oauth2) is ignored | oauth2_alternative at `#/components/securitySchemes/oauth2` | UNSUPPORTED | `the first supported scheme is used` |
| status 'PENDING_APPROVAL' (pending_approval) of status is unknown | unmapped_status | WARN | `statuses.PENDING_APPROVAL: in_progress\|approved\|rejected  (overrides.yml)` |
| status 'RETURNED' (returned) of status is unknown | unmapped_status | WARN | `statuses.RETURNED: in_progress\|approved\|rejected  (overrides.yml)` |
| Swift-Signature: t=<timestamp>,v1=<hmac> scheme (from description); HMAC over "<t>.<raw body>" is verified | signature_timestamped | WARN | `webhook.signature_scheme: plain\|timestamped  (overrides.yml)` |
| GET /v1/accounts/balance: external $ref → {} (available → https://schemas.swiftpay.example/common/Money.json, reserved → https://schemas.swiftpay.example/common/Money.json) | external_ref at `#/paths/~1v1~1accounts~1balance/get` | UNSUPPORTED | `inline the schema if this response matters` |
| beneficiary: 2 variants (IbanBeneficiary, AccountBeneficiary); first (IbanBeneficiary) is used | one_of_first_variant | WARN | `fields.beneficiary.variant: <SchemaName>  (overrides.yml)` |
| beneficiary.address (object) has no source | unmapped_field | WARN | `fields.beneficiary.address.source: "…"  (overrides.yml)` |
