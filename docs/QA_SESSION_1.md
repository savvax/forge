# QA-сессия 1 по кейсу «Генератор интеграций с платёжными провайдерами» — важные вопросы и ответы

Источник: транскрипт встречи QA 1 (3–4.09.2026) + письменные ответы экспертов в чате на «большой вопрос». Ответы сгруппированы по темам, в конце — что это меняет в плане (`claude/hackathon-plan.md`).

## 1. Формат решения, вход и выход

- **CLI или веб-интерфейс?** Рабочего CLI достаточно для максимума баллов, веб не даёт преимущества.
- **Вход — всегда OpenAPI?** Да, только OpenAPI (по условию). PDF/HTML-документация не подаётся.
- **Только выплаты или депозиты тоже?** Только выплаты (payout-методы). Пример в ТЗ — выплаты.
- **Нужно ли обрабатывать доп. поля/эндпоинты спеки (возврат, баланс, вебхуки)?** В спеке могут быть другие поля — зависит от провайдера; есть критерий за работу с нетривиальными спеками. Интегрировать их в класс не обязательно, структуру класса из ТЗ желательно сохранить. Достаточно уведомить пользователя, что в спеке найдены дополнительные поля/эндпоинты.
- **Output должен быть production-ready или можно оставить поля для ручного заполнения?** Можно: например, заголовки с приватными ключами — их нет в документации, разработчик заполняет вручную. URL (sandbox/prod) берутся из спеки. Остальные данные (amount, данные клиента, банк, реквизиты) берутся из объекта operation.
- **Что делать с неподдерживаемым/неоднозначным элементом спеки — пропустить с предупреждением, сгенерировать заглушку или упасть?** На усмотрение команды, если критерии не предписывают. Делать как корректно с точки зрения production-кода: вероятно, отдать ошибку, чтобы пользователь понял, что интеграция не получилась.
- **fixtures.json — достаточно данных или нужны исполняемые тесты?** Фикстуры — файл, который команда заполняет, чтобы продемонстрировать результат при определённых обращениях. Можно дополнять или сжимать. Исполняемые тесты не требуются (но и не запрещены).
- **Откуда брать маппинг статусов/ошибок, если в спеке нет явного соответствия?** У провайдера обычно есть описание статусов; названия могут не совпадать с нашими (in_progress/approved/rejected), но понятны по смыслу (pending/processing и т.п.). Использовать наборы популярных названий статусов. Письменно: канон из задания (см. раздел 7).

## 2. Provider::BaseService и Operation

- **Родительский класс есть в кодовой базе?** Да, `Provider::BaseService` уже есть у них в базе и реализует часть методов. Нам нужно реализовать `create_request`, `fetch_status`, `process_callback`, `check_conditions` — сгенерированный сервис получается из парсинга YAML.
- **Дадут ли реальный класс, точные сигнатуры, хелперы и поля Operation?** Устно: уточнят. Письменно (раздел 7): полный production-класс и harness не обязательны — своя заглушка контракта допустима.
- **Нужно ли реально стучаться к провайдеру?** Нет. Есть абстрактный client, который бьёт по URL с payload. Задача — сгенерировать сервис из YAML, а не подключаться к провайдерам.

## 3. Универсальность

- **Будут ли подавать другую/скрытую спеку на проверке?** Другую подключать не будут, но решение должно работать с любой спекой и не быть заточенным под одну. По коду будут смотреть, что парсится не конкретно этот OpenAPI, а общие конструкции. Совет: найти открытые спеки платёжных провайдеров и проверить на них.
- **Файл настроек под провайдера — привязка к провайдеру и потеря баллов за универсальность?** Письменный ответ в разделе 7: нет, если это общий механизм, а не хардкод в ядре.

## 4. Правила: Ruby, AI, другие языки

- **Версия Ruby?** Желательно как можно новее: 3.x или 4. У них проект на Ruby 3.
- **«Большая часть кода на Ruby» — порог?** Числового порога нет. Основная логика и ядро — на чистом Ruby, код не должен быть фиктивным (Ruby-обёртка для запуска симуляции на другом языке = нарушение). Другие языки — только как дополнение: HTML/CSS для интерфейса, модуль только на Python — допустимо с аргументацией.
- **Какие навыки Ruby проверяются?** Отдельного критерия нет, но код оценивает «условный работодатель». Есть критерий понятности кода: логика разделена, репозиторий понятен — оценят выше, чем «всё в одном файле».
- **AI / нейросети?** Использовать нейросеть, чтобы писать код на Ruby, можно (делать это корректно). Интегрировать ИИ/нейросети/агентов внутрь кода нельзя.
- **Квантовые симуляторы и прочая экзотика?** Не запрещено, но критериев нет; добавлять только если несёт ценность и аргументировано, плюс документировать запуск. Рискованно — лучше вложить ресурс в само решение.

## 5. Оценка, документация, чек-поинты

- **Что понимается под документацией?** Оба артефакта: сгенерированный `INTEGRATION.md` и документация проекта. Документация проекта — для жюри и экспертов с ограниченным временем: какие паттерны использовали, почему такие решения, схема.
- **Если документации нет — остальное можно оценить на максимум?** Да, по критерию документации будет 0, остальные критерии независимы. По каждому критерию 0…N баллов на усмотрение эксперта.
- **Язык документации?** Любой, главное чтобы было понятно экспертам и жюри.
- **Bundle install или Docker?** Стек не ограничен. Критерии оценивают, насколько хорошо задокументировано и описано, как запускать. Сделать удобно и понятно.
- **Как проверяют генератор — запускают код?** Первостепенно читают код в репозитории (умение парсить, интегрировать, проверять, писать доки и фикстуры). Жюри могут развернуть код — поэтому нужна хорошая документация и подготовка к запуску: человек должен зайти, запустить и понять, как использовать.
- **Насколько глубоко делать retry/circuit breaker/очереди/шифрование/alert ops?** Минимум — код не падает на первой ошибке. Чем лучше архитектура, тем лучше оценка; ориентироваться на критерии. Механизмы вне критериев не обязательны, но могут добавить баллов по схожему критерию.
- **Что такое «реализация дополнительных идей» (6 отраслевых баллов)?** То, что понравилось постановщику: лучше проработали задачу, интересная идея, исследование, killer-фичи — то, что выделяет от остальных команд. Обязательно явно подсветить это.
- **Прогресс на чек-поинтах?** Чек-поинты — прежде всего фидбэк от экспертов. Баллы ставятся на финальное решение, важен последний чек-поинт. Первый чек-поинт — понять, над чем работать.
- **Присутствие на чек-поинтах?** Полный состав не обязателен. Третий чек-поинт (воскресенье, с 13:00 MSK) — обязателен хотя бы для одного члена команды. Если пропустил чек-поинт, ничего отправлять не нужно — показать весь прогресс на следующем.
- **Что в презентации?** Короткий спич: как работает решение, что использовали, как строили.

## 6. Сдача и защита

- **Репозиторий: приватный или публичный, один аккаунт?** На стоп-код отправляется одна ссылка на репозиторий; как вести репозиторий (один аккаунт или вся команда) — на усмотрение. Вероятно, публичная ссылка; детали продублируют ближе к стоп-коду и на последнем чек-поинте.
- **Можно ли заливать после 23:00?** Нет. Проверяют историю коммитов; коммит после срока — автоматическая дисквалификация. Коммит ровно в 23:00 — «очень опасно», после 23:00 считается нарушением.
- **Вся команда на защите?** Информацию пришлют ближе к защите.
- **Сертификаты?** Всем командам, загрузившим решение.

## 7. Письменные ответы экспертов на «большой вопрос» (чат, после QA)

**Вопрос 1.** Часть требований в спеке лежит текстом в description (bank_code обязателен для type=sbp; сумма в копейках; детали HMAC — hex/base64, что подписывается — не заданы вообще). Что правильнее: угадывать эвристиками или явно помечать неоднозначность и просить человека дописать файл настроек? Не будет ли такой файл считаться привязкой к провайдеру?

**Ответ:** правильнее второй подход. Из структуры — автоматически; неоднозначное из description — TODO / warning и опциональный **общий** overrides-файл. Это не минус за универсальность, если overrides — механизм (`amount_unit`, `required_if`, `signature_encoding`), а не хардкод в ядре. Эвристики ок как best-effort, но молча угадывать критичное — хуже.
Канон для NovaPay из задания: сумма в копейках; `bank_code` обязателен при `type=sbp`; подпись `HMAC-SHA256(raw body, secret)` → hex.

**Вопрос 2.** Реальный контракт `Provider::BaseService`, harness, сигнатуры, хелперы, поля operation? Что такое `request_method` в `create_request(operation, request_method)`? Откуда маппинг статусов, есть ли канонический словарь Space Payments? Будут ли примеры сервиса и фикстур?

**Ответ:**
- Полный production-класс и harness не обязательны.
- `request_method` — **не HTTP-метод**, а логический тип действия: payment_method шлюза, либо `status` / `check` и т.п.
- Маппинг статусов, если в спеке нет таблицы — канон из задания: `pending`/`processing` → `in_progress`, `completed` → `approved`, `failed`/`cancelled` → `rejected`. Допущения — в `INTEGRATION.md`.
- Примеры сервиса, документации и фикстур уже в описании кейса (`описание.docx`); отдельных не будет.

## 9. Следствия для плана и архитектуры forge

- Веб-UI не делать вообще — CLI достаточно.
- Ruby 3.3/3.4 в Docker — ок («как можно новее»).
- Только payout: третью спеку делать не pay-in, а ещё один payout-провайдер с другой структурой (OpenAPI 3.1 JSON, другая auth/статусы) — pay-in упомянуть только в «что дальше».
- Доп. эндпоинты (balance, cancel, refund) не интегрировать в сервис как обязательную часть контракта, но перечислять в отчёте analyze как «найдено, вне контракта».
- Подход `Finding(confidence) + WARN/TODO + overrides.yml` подтверждён экспертами дословно — это аргумент для питча и README («так рекомендовали организаторы»). Критичные вещи с низкой уверенностью (единицы суммы, кодировка подписи, условная обязательность) **не угадывать молча**: WARN + TODO в коде + строка в `overrides.yml.example`. Некритичные — best-effort с пометкой источника.
- Ключи overrides назвать в терминах экспертов и держать общими: `amount_unit` (minor/major), `fields.<path>.required_if` (`{field: type, equals: sbp}`), `webhook.signature_encoding` (hex/base64), `webhook.signature_payload` (raw_body / fields). NovaPay должен проходить без overrides.
- `request_method` в `create_request(operation, request_method)` — логический тип действия, не HTTP-verb. В сгенерированном сервисе: HTTP-метод всегда из спеки; `request_method` использовать для выбора ветки (payment-method шлюза → тип реквизитов sbp/card/bank_account; `status`/`check` → `fetch_status`). Обновить `docs/CONTRACT.md` и шаблон сервиса.
- Канон NovaPay для golden/reference: копейки (×100), `bank_code` обязателен при `type=sbp`, `HMAC-SHA256(raw body, secret)` → hex. Дефолты анализаторов `Webhooks` (hex) и `Amount` (minor при «копейках») совпадают.
- `rules/status_map.yml` — канон из задания как ядро словаря + синонимы (NEW, SUCCESS, DECLINED, ON_HOLD, captured…).
- В `INTEGRATION.md` добавить раздел «Допущения» (Assumptions): все решения с confidence < 0.8, источник (description/эвристика/override) и как переопределить. Это прямо просили эксперты.
- Секреты (API key, HMAC secret) — плейсхолдеры через credentials с пометкой для ручного заполнения.
- README: паттерны, почему такие решения, схема пайплайна, запуск одной командой (Docker и без); язык — русский допустим.
- Killer-фичи (генерируемый RSpec, мок-сервер, e2e, отчёт с confidence) явно подсветить в README и на питче — под «дополнительные идеи».
- Стоп-код: последний пуш не позднее 00:00 ALA (22:00 MSK) вс 6.09, дальше репозиторий не трогать.
- Присутствие на CP3 (вс 6.09, 15:00 ALA) обязательно.

## 10. QA 2 (6.09) — ответы по контракту `Provider::BaseService` и NovaPay

### Раунд 1

- **Как сервис сохраняет ID операции у провайдера?** Сохранение происходит вне сервиса провайдера. Сервис делает запрос к провайдеру через абстрактный client и отдаёт ответ; реальный запрос к провайдеру не нужен.
- **`process_callback` получает разобранный JSON или сырое тело + заголовки?** Уже разобранный JSON внутри `payload`.
- **Статусы NovaPay (accepted, cancelled, HTTP 402, event vs status)?** Ориентироваться на «Маппинг статусов» из `INTEGRATION.md` в файле задания.
- **Нужен ли отдельный конфиг регистрации провайдера (адрес, авторизация, лимиты)?** Нет. Из OpenAPI провайдера формируются сервис + документация + тестовые фикстуры; адрес, авторизация и т.д. берутся из OpenAPI-документа.
- **Учитывается ли сгенерированный код при подсчёте доли Ruby?** Сама реализация должна быть на Ruby, а не на другом языке.

### Раунд 2

- **Поля `operation`.** Гарантированы `operation.id`, `operation.amount`, `operation.payout_requisite` (JSONB-хеш, не плоские `recipient_phone`/`bank_code`). Формы реквизитов: СБП — `payout_requisite.dig('sbp', 'phone')`, `…('sbp', 'bank_code')`, `…('sbp', 'bank_name')`; карта — часто `payout_requisite['card_number']` (или вложенная card-структура). При необходимости также `gateway`, `provider_operation_key`, `status`.
- **Что возвращает `create_request`.** Не «голый» `success`. Сервис разбирает ответ провайдера и возвращает `success(result: { id: "np_7f3a9b2c" })` (опционально `rate` и т.п.). Платформа делает `provider_operation_key = payload.dig(:result, :id)`. Сырой HTTP-ответ наружу не обязателен.
- **Коды в `failure(:code, 'i18n.key')`.** Первый аргумент — символ в духе HTTP/доменного кода платформы: `:bad_request`, `:unauthorized`, `:unprocessable_entity`, `:too_many_requests`, `:internal_server_error`, `:forbidden`… Второй — i18n-ключ или строка (`'operation.provider_error'`, `'provider.rate_limit'`). Маппить HTTP провайдера → эти коды (401 → `unauthorized`, 429 → `too_many_requests`); свои `:novapay_whatever` не выдумывать.
- **Ветвление по `request_method`.** Это логический метод шлюза (`gateway.payment_method`: `sbp`, `p2p`, …), не HTTP. СБП и карта на платформе обычно разные gateway/payment_method; в одном сервисе — ветки по `request_method` и/или форме `payout_requisite`. Для NovaPay: один сервис, внутри `create_request` ветка по типу получателя / `request_method`.
- **`amount_limit_exceeded` у NovaPay.** Канон: лимит на эту выплату (сумма вне диапазона / max на операцию) → отклонять операцию (`rejected` / validation), не отдавать человеку. Суточный лимит — другие сценарии (`insufficient_balance` / лимиты оркестратора). Иная трактовка — явно описать в `INTEGRATION.md`.

### Следствия для forge (реализовано 6.09)

- `transition` в `BaseService` кладёт в success `result: { id: <provider id> }` — платформа читает `payload.dig(:result, :id)`.
- Поле операции переименовано в `provider_operation_key` (заглушка `Operation`, шаблоны, golden); `provider_operation_id` оставлен алиасом под пример ТЗ.
- Реквизиты читаются через `requisite_for(operation, type)`: вложенная форма `payout_requisite['card']` или плоская `payout_requisite['card_number']`; `requisite_type_for` распознаёт плоскую карту по ключу `card_number`. Канонический реквизит карты — `card_number` (`rules/field_aliases.yml`).
- В `INTEGRATION.md` (раздел «Webhook signature») описано, что платформа передаёт разобранный JSON, и как передать `raw_body:`; без него подпись считается от `JSON.generate(payload)`.
- Статусы, 402, коды `failure`, `amount_limit_exceeded → reject`, ветвление по `request_method`, адрес/авторизация из OpenAPI — уже соответствовали.
