# Процесс разработки forge

Соло-разработчик + кодовые агенты (Claude Code), 3 дня, оценивают код в репозитории.
Методология — **trunk-based development с карточками-задачами и агентами в изолированных worktree**,
приправленная практиками XP: тесты как спецификация, короткие итерации, непрерывная интеграция.

## 1. Роли

| Роль | Кто | Отвечает за |
|---|---|---|
| Lead / Product | John (+ Claude в чате) | Приоритеты, решения (NOTES.md), общение с экспертами, ревью диффов, merge |
| Core | агент | loader, ref_resolver, IR, plan, cli, report, verifier |
| Analyzers | агент | `rules/*.yml`, `lib/forge/analyzers/*`, тестовые спеки CardPay/SwiftPay |
| Renderers | агент | `templates/*.erb`, `lib/forge/renderers/*`, `lib/provider/*`, мок, e2e |
| QA | агент | golden, негативные тесты, покрытие, реальные спеки, CI |
| Docs | агент | README, INTEGRATION-шаблон (текст), docs/, питч-материалы |
| Reviewer | отдельная сессия агента | Ревью диффа по чек-листу, без права писать код |

Подробно (владение файлами, промпты, волны) — `docs/agents/ROLES.md`.

## 2. Единица работы — карточка

Карточка `Txx` в `docs/AGENT_TASKS.md` = одна сессия агента (1–3 часа). В карточке:
**Читать** (какие разделы docs), **Владеет** (файлы, которые можно менять), **Сделать**, **Тесты**
(ожидаемые значения — числа, имена, коды выхода), **DoD**, **Баллы** (какие критерии закрывает).

**Definition of Ready:** есть все ожидаемые значения для тестов; зависимости (карточки выше) смержены
в `main`; человек знает, что будет проверять руками.

**Definition of Done:** `bundle exec rake check` зелёный (rubocop 0, rspec 0 failures, SimpleCov не
ниже порога); тесты карточки написаны и проходят; документация обновлена там, где карточка требует;
запись в `NOTES.md`, если принято решение; коммит с сообщением `<module>: <what>`; отчёт агента
человеку (5–7 предложений).

## 3. Ветки, worktree, merge

- `main` всегда зелёный. Прямых коммитов в `main` нет — только merge из ветки карточки.
- Каждая карточка — ветка `t05-analyzers` в отдельном worktree:
  `git worktree add ../forge-t05 -b t05-analyzers && cd ../forge-t05 && claude`.
- Параллельно запускаются только карточки с непересекающимися списками «Владеет». Волны параллелизма —
  в `docs/agents/ROLES.md`.
- Merge делает человек: `git checkout main && git merge --no-ff t05-analyzers` после `rake check`
  в ветке и чтения диффа (10 минут, чек-лист ревью ниже). Squash не используем — история коммитов по
  задачам понятна жюри.
- Конфликт в `rules/*.yml` или `templates/` разрешает владелец файла (Analyzers / Renderers).

## 4. Чек-лист ревью (человек или Reviewer-агент)

1. Есть ли в `lib/` строка `novapay`, `cardpay`, `swiftpay`, `X-NovaPay`, `sbp`? (`rake guard:vendor`) → нельзя.
2. Есть ли тест на каждое ожидаемое значение из карточки?
3. Понятна ли ошибка пользователю без чтения кода (файл, pointer, hint)?
4. Не появилось ли времени/случайности/абсолютных путей в выходных файлах?
5. Метод > 20 строк или файл > 200 строк без причины?
6. Обновлены ли README/NOTES там, где поведение изменилось?
7. Может ли человек пересказать решение экспертам за 2 минуты по отчёту агента?

## 5. Пирамида качества

| Уровень | Инструмент | Порог / правило |
|---|---|---|
| Стиль | `rubocop` + `rubocop-rspec` + `rubocop-rake` | 0 нарушений, `NewCops: enable` |
| Unit | `rspec`, мини-спеки из литералов | каждый анализатор, loader, resolver, plan, renderer |
| Покрытие | `simplecov` (line + branch) | line ≥ 90 %, branch ≥ 75 %, по файлу ≥ 70 %; отчёт — артефакт CI |
| Контракт | `spec/reference_spec.rb` | все элементы примера ТЗ присутствуют в сгенерированном сервисе/доке/фикстурах |
| Golden | `spec/golden_spec.rb` | байт-в-байт для novapay, cardpay, swiftpay (с overrides и без) |
| Негативные | `spec/cli_spec.rb`, `spec/fixtures/broken/*` | каждая ошибка → класс, pointer, hint, код выхода |
| Сгенерированный код | его собственный spec (WebMock) | зелёный для всех трёх спек, запускается в CI |
| e2e | `bin/e2e` (мок + сервис + webhook) | `operation approved ✓`, exit 0 |
| Реальные спеки | `spec/real_specs_spec.rb` (тег `:real`) | не падает; роли/auth совпадают с `docs/REAL_SPECS.md`; отчёты сохранены |
| Детерминизм | `rake determinism` | два прогона `generate` → одинаковый `sha256sum` выходов |
| Лицензии | `rake licenses` | все гемы MIT/Apache/BSD/Ruby |

Подробности и примеры тестов — `docs/TESTING.md`.

## 6. Непрерывная интеграция

`.github/workflows/ci.yml`: `lint` → `test` (с артефактом coverage) → `generate` (матрица трёх спек,
golden) → `generated-specs` (rspec на output) → `e2e` → `docker` (build + `bin/forge help`).
Job `real-specs` — по расписанию/вручную, `continue-on-error: true`, публикует отчёты как артефакт.
Локальный эквивалент — `bundle exec rake ci`.

## 7. Документация как код

Документы — это часть продукта (критерии «понятность», «инструкция», «документация 13 баллов»).
Слои (по Diátaxis):

| Слой | Документ | Владелец | Когда обновляется |
|---|---|---|---|
| Tutorial | `README.md` → «Быстрый старт» (Docker и без) | Docs | при изменении CLI; финал в T16 |
| How-to | `README.md` → «Как переопределить решение (overrides)», `examples/overrides/*.yml` с комментариями | Analyzers | T09, T13, T14 |
| Reference | `docs/ARCHITECTURE.md`, `docs/RULES.md`, `docs/CONTRACT.md`, `docs/OUTPUT_FORMAT.md`, `bin/forge help` | Core/Analyzers/Renderers | вместе с кодом карточки |
| Explanation | `NOTES.md` (решения ADR-lite), `README.md` → «Почему без нейросети», «Ограничения» | Lead | по факту решения |
| Оценка | `README.md` → «Критерий → где смотреть» | Docs | T16, T17 |
| Сгенерированная | `output/<p>/INTEGRATION.md`, `report.txt` | Renderers | шаблон в T11, допущения — обязательный раздел |
| Питч | `docs/PITCH.md` (7 слайдов + скрипт демо) | Lead | T20 |

Правила:
- Язык: русский для повествования, английский для кода, идентификаторов, коммитов и вывода CLI
  (формат отчёта задан ТЗ на английском). Заголовки `INTEGRATION.md` — как в ТЗ (русские).
- Каждый документ начинается с одного абзаца «зачем это читать». Никаких «(план)» в README к CP3.
- Команды в README — только те, что реально проверены в CI (`rake readme:check` запускает блок
  «Быстрый старт» из README и сравнивает код выхода).
- Формат записи в `NOTES.md`: `### D-07 · Заголовок` → Контекст / Решение / Альтернативы / Следствия
  (4 строки). Обратная связь экспертов — раздел «CPx» с датой, дословно, затем «что меняем».
- Сгенерированная документация проверяется тестом: заголовки и таблицы reference присутствуют,
  раздел «Допущения» перечисляет каждое WARN с источником и ключом overrides.

## 8. Ритм дня

- Утро: 10 минут — обновить `docs/PLAN.md` (что реально закрыто), выбрать волну на день.
- Каждые 2–3 часа: merge готовых карточек, `rake ci`, пуш в `origin/main` (бэкап и история для жюри).
- После чек-поинта: 15 минут — записать фидбэк в `NOTES.md`, переоценить cut-list.
- Вечер: `git tag cp1`/`cp2`/`cp3` на состояние, показанное экспертам.
