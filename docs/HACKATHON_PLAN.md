## Задача
Инструмент на Ruby: на вход OpenAPI-спека платёжного провайдера (`provider_api.yaml`, пример — NovaPay Payout API: POST /payouts, GET /payouts/{id}, POST /payouts/{id}/cancel, POST /webhooks/payout с HMAC-SHA256 в `X-NovaPay-Signature`, GET /balance, auth `X-API-Key`, `Idempotency-Key`), на выход:
1. `novapay_service.rb` по контракту `Provider::BaseService` (`check_conditions`, `create_request`, `fetch_status`, `process_callback`; константы `BASE_URL`, `STATUS_MAP`, `ERROR_MAP`).
2. `INTEGRATION.md` (авторизация, таблица методов, маппинг статусов pending/processing→in_progress, completed→approved, failed/cancelled→rejected, обработка ошибок, ProviderGateway config, подпись webhook, допущения).
3. `fixtures.json` (request/response_201/response_422, fetch_status, callback, callback_failed с `expected_operation_status`).
4. CLI: `./integrate --spec provider_api.yaml --provider novapay --lang ruby` с прогресс-выводом.

Ограничения: только open-source, большинство кода на Ruby, **нейросети внутри проекта запрещены** (продукт не вызывает LLM; AI-ассистированная разработка разрешена — подтверждено на QA 1). Нарушение → дисквалификация.

## Стратегия
Ядро (60 баллов) — сквозной пайплайн для NovaPay к ночи пятницы. Дифференциаторы, которых не будет у большинства:
1. Доказательство работоспособности: генерируемый RSpec (WebMock + fixtures) и мок-сервер провайдера (Sinatra) из той же спеки; e2e `create → webhook → approved` на питче.
2. Объяснимый движок правил: confidence + WARN/UNSUPPORTED в отчёте, необязательный общий `overrides.yml` (`amount_unit`, `required_if`, `signature_encoding`). **Подход подтверждён экспертами письменно** — цитировать на питче как «рекомендованный организаторами»; «без нейросетей» → детерминированно, аудируемо.
3. Универсальность на 3+ payout-спеках (NovaPay + CardPay: bearer, карта, рубли строкой, статусы NEW/SUCCESS/DECLINED/ON_HOLD, обёртка data, HMAC-SHA512 base64 + третья: другой payout-провайдер в OpenAPI 3.1 JSON) с golden-тестами. Pay-in не нужен (задача — только выплаты).
4. DX одной команды: `bin/forge generate`, Docker, понятный отчёт и ошибки, README.
Порядок: NovaPay сквозной → ширина → доказательства и упаковка. Веб-UI не делать: CLI достаточно для максимума баллов (QA 1).

## Архитектура (рабочее имя `forge`)
Load (YAML/JSON, $ref) → IR (Data.define) → Analyze (analyzers: endpoint_roles, auth, statuses, errors, webhooks, amount, fields; словари в `rules/*.yml`) → Plan (`IntegrationPlan` + overrides) → Render (ERB: service, spec, docs, fixtures, mock) → Verify (`ruby -c`, rspec output) → Report.
Гемы: thor, faraday, rspec, webmock, rubocop, sinatra + rackup. Ruby 3.3 в Docker. Заглушка `lib/provider/base_service.rb` (client, success/failure, approve/reject_operation, credentials) — реальный класс не дадут, заглушка = контракт.
Правила из QA 1: доп. эндпоинты (balance/cancel/refund) в сервис не встраивать как часть контракта, а перечислять в отчёте; критичные неподдерживаемые элементы → явная ошибка, некритичные → WARN; критичное с низкой уверенностью (единицы суммы, кодировка подписи, условная обязательность) не угадывать молча — WARN + TODO + overrides; секреты — плейсхолдеры для ручного заполнения; `request_method` в `create_request` — логический тип действия (payment-method шлюза / status / check), не HTTP-verb; `INTEGRATION.md` получает раздел «Допущения». Канон NovaPay: копейки, `bank_code` при `type=sbp`, HMAC-SHA256(raw body) → hex. Канон статусов: pending/processing→in_progress, completed→approved, failed/cancelled→rejected.

## Вопросы на QA (3.09, 21:30 ALA) — статус после QA 1 и письменных ответов
1. `Provider::BaseService` — класс существует в их базе, но полный класс и harness не обязательны; наша заглушка — контракт. Примеры сервиса/доки/фикстур — только из описания кейса.
2. Модель `operation` — не уточняли; берём из примера ТЗ. `request_method` = логический тип действия (payment-method / status / check), не HTTP-метод.
3. Баллы на финальное решение.
4. Скрытых спек нет, но код будут читать на предмет универсальности; вход только OpenAPI.
5. LLM в продукте нельзя, AI-ассистенты при разработке — можно.
6. Только payout.
7. Одна ссылка на репозиторий на стоп-код (вероятно публичный), Docker не обязателен, стек не ограничен; детали продублируют.
8. Слоты — через модератора; на первом чек-поинте важен фидбэк, не баллы.
9. Overrides-файл — не привязка к провайдеру, если это общий механизм; неоднозначное из description → TODO/WARN + overrides; критичное молча не угадывать.
Полные ответы: `claude/qa-session-1.md`.
