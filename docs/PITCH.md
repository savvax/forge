# Питч forge — 7 слайдов (текст)

1. **Проблема.** Каждый новый провайдер выплат — дни ручного чтения спеки и переписывания одного и того же
   сервиса. Ошибки — в единицах суммы, статусах и подписи webhook.
2. **Решение.** `bin/integrate --spec provider.yaml --provider name --lang ruby` → сервис по контракту
   `Provider::BaseService`, RSpec, гайд, фикстуры, мок, отчёт. Один прогон — 1 секунда.
3. **Как.** Шесть стадий: Load → IR → Analyze → Plan → Render → Verify. Знание о платежах — только в
   `rules/*.yml` (роли, статусы, ошибки, поля, единицы, подпись). Ни одной строки провайдера в коде
   (`rake guard:vendor`).
4. **Честность вместо угадывания.** Из структуры — автоматически (confidence). Из текста description —
   WARN + TODO + строка для `overrides.yml`. Неподдерживаемое — UNSUPPORTED, а не крэш. Детерминизм: два
   прогона байт-в-байт.
5. **Доказательства.** Сгенерированный RSpec зелёный для трёх спек; мок из той же спеки + e2e
   `create → webhook → approved`; golden-тесты; 216 тестов, покрытие 97 %; CI за 15 с.
6. **Универсальность.** NovaPay (ТЗ), CardPay, SwiftPay 3.1 + 7 реальных API (Stripe, Adyen ×2, PayPal,
   Paystack, Square, Plaid) — все анализируются, WARN закрываются overrides.
7. **Что дальше.** Pay-in тем же пайплайном, выбор `oneOf` в overrides, статус через POST, JSON-Schema
   валидация фикстур, шаг CI «новый провайдер → PR с сервисом и тестами».

Killer-фичи под «дополнительные идеи»: генерируемый RSpec, мок + e2e, отчёт с confidence и допущениями,
overrides как рекомендованный механизм, реальные API, детерминизм без LLM.
